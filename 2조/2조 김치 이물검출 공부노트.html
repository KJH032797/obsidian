01핵심 개념

Object Detection과 YOLO

사진 한 장에서 어디에(BBox), 무엇이(Class), 얼마나 확신하는지(conf)를 한 번에 내놓는 문제예요. 우리는 YOLO11 계열을 썼어요. 크기는 n(가장 가볍고 빠름) < s 순서이고, Baseline은 yolo11n이에요.

라벨 = 사진 + TXT 한 쌍

사진마다 같은 이름의 .txt가 있고, 한 줄이 박스 하나예요. 형식은 class x_center y_center width height이고, 좌표는 사진 크기로 나눈 0~1 값이에요. 박스가 하나도 없는 빈 TXT는 배경(이물 없음) 사진이에요.

IoU: 박스가 얼마나 겹치나

conf (확신도)

모델이 박스마다 붙이는 0~1 점수예요. 실패 분석은 conf ≥ 0.25인 예측만 봤어요. conf를 낮추면 더 많이 찾지만(R↑) 헛박스도 늘어요(P↓).

Precision · Recall · mAP

Precision (P, 정확도)

모델이 "이물이다"라고 한 것 중 진짜 이물인 비율. 헛박스(FP)가 많으면 내려가요.

Recall (R, 찾기)

진짜 이물 중 모델이 찾은 비율. 놓친 것(FN)이 많으면 내려가요. 이물 검출에선 놓치는 게 더 위험해요.

mAP50

IoU 0.5 기준으로 Class별 AP(P-R 곡선 아래 면적)를 구해 평균. "찾았나"에 가까움.

mAP50-95 (우리 주 지표)

IoU 0.50, 0.55 … 0.95 기준 AP의 평균. 박스 위치까지 정확해야 높아요. Final 선택 기준.

실패 유형 4가지 (failure_analyzer.match_boxes)

유형판정 조건 (conf ≥ 0.25)쉬운 말
TPIoU ≥ 0.5, Class 같음맞힘
CLASSIoU ≥ 0.5, Class 다름위치는 맞는데 이름을 틀림
BBOXIoU 0.1~0.5, Class 같음이름은 맞는데 박스가 비뚤어짐
FP어떤 정답과도 안 겹침헛박스
FN끝까지 짝이 없는 정답놓침 (가장 큰 문제)

크기(small/medium/large) 경계는 Class별로 전체 900장 박스 크기의 1/3·2/3 지점이에요. Val과 Test에 같은 경계를 써서 비교할 수 있어요.

과적합(Overfitting) 확인법

Train은 계속 좋아지는데 Val이 나빠지기 시작하면 외우기만 하는 상태예요. train loss는 계속 내려가는데 val loss가 다시 올라가는 지점이 신호예요. 그래서 best 가중치는 Val 기준으로 고르고, patience(개선이 없으면 멈추는 epoch 수)를 둬요. 우리 Baseline은 70 epochs · patience 30이고, 예비 학습의 best가 70~75 epoch 근처여서 70으로 정했어요.

확인 필요실제 train/val loss 곡선 숫자는 이 자료에 없어요. 과적합 여부를 물으면 Training 담당(이상직)의 results.csv/results.png로 답해야 해요.

03Split · 촬영 묶음 단위로 나누기

Data · 장세훈 (4번), 정책·코드 보조 · 박하나

왜 사진 단위로 나누면 안 되나 (누수)

같은 이물 세트를 김치 위에서 옮겨 가며 찍었고, 5분 넘게 쉴 때만 이물을 바꿨어요. 그래서 같은 묶음 사진은 사실상 같은 문제예요. 사진 단위로 나누면 같은 이물이 Train과 Val에 함께 들어가서 "이미 본 문제"를 맞히게 돼요.

묶음 만드는 법 (split_builder.py)

  1. 파일명(YYMMDD_HHMMSSffffff) = 촬영 시각 → 시간순 정렬
  2. 앞 사진과 5분(300초) 넘게 떨어지면 새 묶음 → 18개 묶음 T00~T17
  3. MD5가 같은 파일, pHash 거리 ≤ 5인 거의 같은 사진이 다른 묶음에 있으면 묶음 병합
  4. 묶음 단위로 배정 후 검증 (같은 묶음이 두 split에 없음, MD5 겹침 없음, 장수 확인)

  • evaluate_detector.check_inputs(): split="test"인데 allow_test=False면 PermissionError
  • 13_evaluate_final_test.py: final_metrics.csv가 이미 있으면 멈춤 (--force만 예외, 사유 기록)
  • 13b: 결과 파일 있으면 멈춤, test 사진은 옮기거나 지우지 않음 (목록 txt만 만듦)

10예상 질문과 답

처음 16개는 가장 자주 나올 질문이고, 아래에 주제별 질문을 더 모았어요. 눌러서 답을 확인하세요.

자주 나올 질문

Q. 점수가 낮은데 왜 믿을 수 있다고 하나요?

4가지 조건을 지켰기 때문이에요. 정답을 3단계로 검수했고, 같은 촬영 묶음이 Train과 평가에 섞이지 않게 나눴고, Baseline을 다시 재도 같은 값이 나왔고, Final은 Val로 먼저 고른 뒤 Test는 한 번만 열었어요. 그래서 Val .446과 Test .412가 비슷하게 나왔어요.

Q. Recall이 0.781에서 0.444로 떨어졌는데 모델이 나빠진 건가요?

아니에요. 0.781은 사진 단위로 나눠서 같은 이물 세트가 Train과 Val에 함께 있던(누수) 값이에요. 묶음 단위로 다시 나누니 처음 보는 이물에서의 진짜 값 0.444가 나왔어요. 부풀린 점수를 걷어낸 거예요.

Q. 왜 묶음을 조금만 잘라서 75장을 맞추지 않았나요?

자르면 같은 이물 세트가 양쪽에 들어가 다시 누수가 생겨요. 장수보다 누수 방지를 우선해서 Val 66장으로 갔어요. T17·T00도 같은 이유로 안 잘랐어요.

Q. Bridge Holdout은 뭐예요?

T09·T11·T16 150장으로, 학습과 튜닝 어디에도 안 쓴 깨끗한 기준점이에요. 교과 14에서 비교용으로 써요.

Q. 왜 해상도(imgsz)부터 바꿨어요?

Baseline이 놓친 82개 중 73%가 작은 이물이었어요. 640으로 줄이면 30px 이물이 약 4px이 돼서 안 보이니, 해상도를 키우면 덜 놓칠 거라는 가설을 세웠어요.

Q. +0.02 기준은 어떻게 정했어요?

Val 66장은 운으로도 ±0.01 정도 흔들려서, 그보다 확실히 큰 차이만 개선으로 인정하려고 정했어요. 결과를 보기 전(10/16)에 정했어요.

Q. EXP004가 더 높은데 왜 EXP003이에요?

EXP004는 해상도와 모델을 둘 다 바꿔서 한 변수 비교 후보가 아니라 참고로 뒀어요. 계산량도 커요. 공식 이유는 박하솔 확인

Q. Test를 왜 한 번만 돌려요?

여러 번 보고 고치면 Test에 맞춘 점수가 돼요. 그래서 allow_test와 덮어쓰기 금지로 코드에서 막았어요.

Q. 75장이랑 74장 결과가 왜 두 개예요? 13b는 튜닝 아니에요?

애매한 라벨 1장을 빼는 정책을 13번이 안 지켜서, 75장 결과는 그대로 두고 74장을 따로 남겼어요. 모델·imgsz·conf는 같고 사진 목록만 달라서 튜닝이 아니에요. 차이는 .412 → .417로 작아요.

Q. Val P는 .948인데 Test P는 왜 .605예요?

Test에서 나뭇가지를 벌레·나뭇잎으로 헷갈린 게 많아서(CLASS 72개 중 56개) 벌레·나뭇잎 Precision이 떨어졌어요. 파·고추가 1개뿐인데 0점이라 평균을 깎은 것도 있어요. 주 지표 mAP50-95는 .446 → .412로 거의 유지됐어요.

Q. 병해는 왜 하나도 못 찾아요?

병해 465개 중 Train에는 163개(35%)뿐이고 236개(51%)가 Bridge 묶음에 있어요. 크기와 상관없이 거의 다 놓쳐요. 모델보다 학습 데이터 부족 문제라 Train에 병해 사진을 더 넣는 게 다음 할 일이에요.

Q. Class 6는 왜 "평가 불가"예요?

파·고추의 99%가 T00 한 묶음에 있어서 Val·Test에 각 1개뿐이에요. 맞으면 1, 틀리면 0이라 숫자로 결론을 내면 안 돼요. 묶음을 쪼개면 누수가 생겨서 못 나눴어요.

Q. FN·FP·CLASS·BBOX 기준이 뭐예요?

conf ≥ 0.25 예측만 봐요. IoU ≥ 0.5 + 같은 Class = TP, IoU ≥ 0.5 + 다른 Class = CLASS, IoU 0.1~0.5 + 같은 Class = BBOX, 아무 정답과 안 겹침 = FP, 짝 없는 정답 = FN.

Q. 과적합은 어떻게 확인했어요?

train loss는 내려가는데 val loss가 올라가는지 봐요. best 가중치는 Val 기준으로 저장하고 patience 30을 뒀어요. 그리고 Val과 처음 보는 Test의 차이가 −0.034로 작아서 Val에 과하게 맞춘 건 아니라고 말할 수 있어요. loss 곡선은 Training 확인

Q. 고무장갑은 어떻게 처리했어요?

Class 4는 번호만 남은 미사용 Class예요. 장갑을 이물로 잡는 오검출을 막으려고 처리했어요. 배경으로 박스 삭제인지, Class 1로 합쳤는지 팀 답 통일 필요

Q. Auto Label을 그대로 쓰면 안 되나요?

Test Recall이 .466이라 절반 가까이 놓치고 병해는 못 찾아요. 그래서 모델 결과는 후보로만 쓰고, 교과 7 프로그램에서 사람이 수정·승인해요.

개념·지표

Q. Precision과 Recall 중 뭐가 더 중요해요?

이물 검출에서는 Recall이에요. 헛박스(FP)는 사람이 한 번 더 보면 되지만, 놓친 이물(FN)은 그대로 제품에 들어가요. 우리 Test Recall이 .466이라 모델만으로는 부족하고 Human Review를 붙인 이유도 이거예요.

Q. mAP50 말고 mAP50-95를 주 지표로 쓴 이유는?

mAP50은 박스가 절반만 겹쳐도 맞힌 걸로 쳐서 "찾았나"만 봐요. mAP50-95는 IoU 0.50~0.95를 모두 평균해서 박스 위치까지 정확해야 높아요. 더 엄격한 기준으로 고르려고 썼어요.

Q. 병해 Precision이 1.000인데 좋은 거 아니에요?

아니에요. 모델이 병해라고 예측한 게 거의 없어서, 몇 안 되는 예측이 맞았을 뿐이에요. Recall이 0이라 실제로는 거의 다 놓친 상태예요. P와 R을 항상 같이 봐야 해요.

Q. 실패 분석에서 conf 0.25를 쓴 이유는?

예측 기본값을 그대로 써서 Baseline Val 분석과 Test 분석을 같은 기준으로 비교하려고요. 결과를 보고 conf를 바꾸지 않았어요.

Q. Ultralytics가 그려주는 Confusion Matrix는 왜 안 썼어요?

낮은 conf 기준으로 그려져서 배경 쪽 헛박스가 실제보다 크게 보였어요. 그래서 conf 0.25 기준으로 직접 짝지은 실패 분석(09번)을 썼어요.

Q. YOLO 라벨 좌표는 픽셀이에요?

아니에요. class x_center y_center width height를 사진 너비·높이로 나눈 0~1 값이에요. 그래서 imgsz를 640에서 1280으로 바꿔도 라벨은 그대로 써요.

Q. Leaf는 Recall .857인데 Precision .319예요. 무슨 뜻이에요?

진짜 나뭇잎은 잘 찾지만, 나뭇잎이 아닌 것(주로 나뭇가지)도 나뭇잎이라고 많이 불렀다는 뜻이에요. Test CLASS 혼동 중 25개가 branch → leaf였어요.

교과 7 데이터

Q. 778장이나 고쳤으면 처음 라벨이 엉망이었던 거예요?

"한 번이라도 손댄 사진"을 센 숫자라서 느슨한 박스를 딱 맞게 고친 것도 포함돼요. 그중 큰 건 빠진 이물 350개를 새로 추가한 거예요. 그만큼 3단계 검수가 실제로 효과가 있었다는 근거로 말하면 돼요.

Q. 자동 검사는 무엇을 검사했어요?

심각 등급과 확인 필요 등급으로 나눠 라벨 문제를 찾고, 심각 등급이 0건이어야 FINAL을 만들었어요. 세부 검사 항목은 장세훈 확인

Q. 배경(빈 라벨) 사진은 왜 넣었어요?

이물이 없는 사진에서는 아무것도 잡지 않도록 배우게 하려고요. 26장이 있고, 오탐을 줄이는 데 써요.

Q. 데이터는 왜 레포에 없어요?

NDA 때문이에요. 라벨을 커밋했다가 되돌린 적이 있어서, 레포에는 코드와 목록(manifest)·리포트만 올려요.

Split

Q. 묶음 기준을 왜 5분으로 했어요?

촬영한 사람에게 확인해 보니 5분 넘게 쉴 때 이물 세트를 바꿨어요. 25장마다 김치 종류는 바뀌지만 이물은 그대로라 25장 단위는 경계로 쓰지 않았어요.

Q. pHash는 뭐예요?

사진의 "지문" 같은 값이에요. 파일이 달라도 거의 같은 장면이면 거리가 작아요. 거리 5 이하이면 같은 묶음으로 합쳤고, 최종 묶음 경계끼리는 거리가 14~24라서 경계를 넘는 누수가 없다고 확인했어요.

Q. Split 버전이 왜 이렇게 많아요 (v1, v4-A, v4-B)?

v1은 원래 validation 사진을 Val로 살리려고 묶음을 쪼갰고, v4-A는 사진 단위라 누수가 있었어요. 둘 다 같은 이물이 Train과 평가에 함께 들어가는 문제가 있어서, 묶음을 절대 안 쪼개는 v4-B로 확정했어요 (2026-10-19).

Q. 원본 데이터셋의 validation을 그대로 쓰면 되지 않아요?

원본 validation 180장이 묶음마다 14~30%씩 흩어져 있어서, 그대로 쓰면 같은 묶음이 Train과 Val으로 갈라져요. 실제로 180장 중 135장이 Train 사진과 60초 이내에 찍힌 사진이었어요.

Q. Val과 Test는 뭐가 달라요?

Val은 모델 비교·Final 선택에 여러 번 써요. Test는 Final을 정한 뒤 딱 한 번만 열어요. 그래서 Val 점수는 "고르는 데 쓴 점수", Test 점수가 "처음 보는 데이터에서의 성능"이에요.

Q. Test에 정상 김치가 없으면 오탐은 어떻게 확인해요?

Test에서는 못 봐요. 정상 김치 묶음이 T01·T02·T03 셋뿐이라서요. 대신 Val의 정상 김치 15장에서 헛박스가 0개였다는 것으로 확인했고, Test 쪽은 한계로 적었어요.

Q. 병해를 살리려고 Bridge 묶음을 바꾸는 방법은 없었어요?

있어요. Bridge의 T09를 T06과 맞바꾸는 v5 후보를 만들었지만 실제 데이터로 돌리기 전이고, 최종은 v4-B로 확정했어요. 교과 11·14에서 다시 볼 수 있는 선택지예요.

Q. K-Fold 교차검증은 안 했어요?

이번엔 고정 Split 하나로 진행했어요. 묶음이 18개뿐이라 Fold마다 Class 구성이 크게 흔들리고, Test·Bridge를 고정해 두는 원칙과도 맞지 않아서예요. 대신 결과의 불확실성(Val 66 · seed 1회)을 함께 말해요.

Baseline·학습

Q. 왜 yolo11n으로 시작했어요?

가장 가볍고 빨라서 기준점으로 좋아요. 그다음 실험에서 크기(s)나 해상도를 하나씩 바꿔서 얼마나 좋아지는지 봤어요.

Q. batch를 8로 작게 잡은 이유는?

imgsz를 1280까지 올려도 GPU 메모리에 들어가야 같은 batch로 공정하게 비교할 수 있어서예요. 실험마다 batch가 다르면 변수가 2개가 돼요.

Q. Smoke Test는 뭐예요?

본 학습 전에 아주 짧게 돌려서 데이터 경로, 라벨, 설정이 제대로 연결되는지만 보는 시험 운전이에요.

Q. "재현 성공"이 왜 중요해요?

같은 가중치·데이터로 다시 재도 같은 숫자가 나와야 이후 실험 비교를 믿을 수 있어요. 한때 옛 평가 코드 때문에 값이 달랐는데, main 버전으로 되돌린 뒤 팀 값(mAP50-95 .3445)과 일치했어요.

실험·Final 선택

Q. 960과 1280 중 왜 1280이에요?

Val mAP50-95가 960은 .423, 1280은 .446으로 1280이 더 높았고 후보 중 4개 지표 모두 1등이었어요. 다만 1280은 계산량이 Baseline의 약 4배라서, 현장 속도가 문제면 960(EXP001)이 대안이에요.

Q. md5 잠금은 뭐예요?

학습에 쓰는 train/val 목록 파일의 해시값이에요. 실험마다 이 값이 같아야 학습이 시작되게 해서, 데이터가 몰래 바뀐 채로 비교되는 걸 막았어요.

Q. 증강이나 다른 하이퍼파라미터는 왜 안 바꿨어요?

한 번에 하나만 바꾸는 규칙이라, Baseline 실패 분석에서 가장 큰 원인(작은 이물)과 연결되는 해상도와 모델 크기부터 봤어요. 나머지는 다음 단계 후보예요.

Q. seed 한 번만 돌렸는데 결과를 믿어도 돼요?

큰 차이(mAP50-95 +0.101)는 믿을 만하지만, 작은 차이는 불확실하다고 스스로 적었어요. 그래서 +0.02 기준을 미리 정해서 운으로 생기는 흔들림(±0.01)보다 큰 것만 인정했어요.

Frozen Test

Q. Test 결과를 보고 바꾼 게 하나도 없어요?

없어요. 16번 분석은 "왜 틀렸나"를 보는 분석만 했고, 모델·설정·conf는 그대로예요. 74장 재평가도 평가 사진 목록만 정책대로 맞춘 거예요.

Q. Val .446 → Test .412, 이 차이는 괜찮은 거예요?

−0.034로 작아요. Val로 모델을 골랐는데도 처음 보는 묶음에서 비슷하게 나왔으니, Val에 과하게 맞춰지지 않았다는 근거예요.

Q. Test에서 branch는 Val보다 오히려 좋아요 (.808). 왜요?

Test의 branch는 medium 크기가 64%로 쏠려 있어서 찾기 쉬운 편이었어요. Split마다 크기 구성이 다르니 Class별 숫자는 구성과 같이 봐야 해요.

Q. Test 75장 중 몇 장에서 실패가 있었어요?

71장이에요. 실패는 FN 93 · FP 87 · CLASS 72 · BBOX 4로, 모두 김치+이물 장면이었어요.

현장 적용·다음 단계

Q. 이 모델을 실제 공장에 바로 쓸 수 있어요?

단독으로는 어려워요. Recall .466이라 절반 가까이 놓치고 병해는 못 찾아요. 지금은 사람 검수를 돕는 후보 생성(Auto Label) 용도이고, 교과 11·14에서 데이터 보강과 현장 확인이 필요해요.

Q. 교과 11·14에서는 뭘 해요?

교과 11에서는 병해·파·고추·정상 김치를 다른 장면으로 더 촬영해 데이터 한계를 풀고, 교과 14에서는 Bridge 150장과 현장(Jetson 속도 포함)으로 다시 확인해요.

Q. Auto Label 결과를 교과 7 도구에서 바로 열 수 있어요?

네. 모델이 YOLO TXT 형식으로 저장해서 교과 7 프로그램이 그대로 불러와요. 사람이 수정·승인하고 검수 통계를 기록해요. 통계 항목은 김준형 확인

코드리뷰

Q. Test를 실수로 여는 걸 코드에서 어떻게 막았어요?

evaluate_detector.check_inputs()가 split="test"인데 allow_test=False면 PermissionError를 내요. 13번은 결과 파일이 이미 있으면 멈추고, --force는 사유를 남겨야 해요.

Q. 13번을 고치지 않고 13b를 따로 만든 이유는?

13번을 고쳐서 다시 돌리면 공식 1회 결과가 덮어써져요. 그래서 75장 결과는 그대로 두고, 74장은 별도 스크립트와 별도 결과 파일로 남겼어요.

Q. 크기 경계(small/medium/large)는 어디서 가져와요?

원래 split_report.md에서 읽는데 v4 리포트에 경계 줄이 없었어요. 그래서 같은 규칙(Class별 900장 박스 크기의 1/3·2/3 지점)으로 다시 계산해 Val과 Test에 똑같이 썼어요.

Q. 테스트 코드는 있어요?

네. tests/test_split_builder.py(Split 검증)와 tests/test_failure_analyzer.py(실패 판정, 16개 통과)가 있어요.

Q. 실패 사례 이미지는 왜 커밋에 없어요?

.gitignore가 *.jpg를 막고 있어서요. 데모 이미지는 팀 허락을 받고 git add -f로 올리기로 했어요.
