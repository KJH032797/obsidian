## 순서대로 진행하는 14단계

### 1. 만들고 싶은 기능을 먼저 내 말로 정의합니다

생성형 AI에게 곧바로 Python 코드를 요청하지 않습니다. 먼저 **무엇을, 왜 만들고, 무엇이 성공인지**를 한글로 작성합니다.

- **목표:** 배추김치 이물질 검출용 YOLO 학습 파이프라인이 최소한 정상 실행되는지 확인합니다.
- **입력:** 이미지, 정답 라벨, 클래스 목록, 데이터 저장 경로
- **출력:** 데이터 점검 결과, YOLO 데이터셋 설정, 짧은 학습 실행 기록
- **성공 조건:** 데이터 오류를 찾아 보고하고, 올바른 데이터로 짧은 학습을 오류 없이 실행하며, 결과 파일과 로그를 남깁니다.

처음에는 완벽한 설계보다 **목표와 입력·출력·성공 조건을 자신의 말로 구별하는 것**이 중요합니다.

### 2. 작은 전체 흐름을 한글로, 코딩하듯 작성합니다

예를 들어 다음처럼 작성합니다.

1. 이미지 폴더와 라벨 폴더를 읽는다.
2. 이미지가 열리는지 검사한다.
3. 이미지·라벨의 대응 관계와 클래스 번호, BBox 좌표를 검사한다.
4. 점검 결과를 출력하고 치명적인 오류가 있으면 중지한다.
5. Train/Validation 데이터를 준비하고 `data.yaml`을 확인한다.
6. YOLO 사전학습 모델을 불러와 아주 적은 데이터와 짧은 Epoch로 실행한다.
7. 오류 여부와 출력 파일, 실행 로그를 확인한다.

이 단계의 결과는 **실행 가능한 Python 코드가 아니라 한글 의사코드(설계 초안)**입니다.

### 3. 생성형 AI에게 첫 번째 피드백을 요청합니다

**프롬프트 예시 ① — 최소 뼈대 설계**

> 나는 YOLO 기반 배추김치 이물질 검출 프로젝트를 준비하고 있습니다. 
> 먼저 `데이터 Audit → YOLO Dataset 구성 → 작은 Smoke Test`까지만 만들고 싶습니다. 
> Python 코드는 아직 작성하지 마세요. 
> 위 작업을 **한글 의사코드**로, 실제로 코딩하는 듯한 순서로 작성해 주세요. 
> 각 단계의 입력, 처리, 출력, 실패 조건을 간단하게 표시하고, 빠뜨린 점이나 순서상 문제가 있다면 이유를 설명해 주세요. 
> 모델 성능을 높이는 방법보다 **데이터와 학습 파이프라인이 정상 실행되는지**에 집중해 주세요.

AI의 답변을 정답으로 확정하지 않고 자신의 초안과 비교합니다.

### 4. 내가 다시 생각하고 두 번째 요청으로 세분화합니다

답변을 읽으며 **빠진 예외 상황**과 **내가 이해하지 못한 단계**를 찾아 다시 질문합니다.

**프롬프트 예시 ② — 누락 조건 보완**

> 앞의 한글 의사코드를 다음 조건에 맞게 더 세분화해 주세요. 
> 데이터 Audit에서 이미지 열기 실패, 이미지와 라벨 파일 불일치, 잘못된 클래스 ID, YOLO 좌표 범위 오류를 검사하고 싶습니다. 
> 이물이 없는 정상 이미지의 빈 라벨은 오류로 취급하지 않도록 구분해 주세요. 
> Train/Validation 사이에 같은 원본이나 거의 동일한 이미지가 섞이지 않게 확인해 주세요. 
> 각 단계별 정상 사례와 실패 사례를 적어 주세요. 
> 여전히 Python 코드는 작성하지 말고 한글 의사코드로 답변해 주세요.

이 과정을 한 번 이상 반복해 **내가 설명할 수 있는 설계**를 만듭니다.

### 5. 최소 기능만 한 개의 Python 파일로 만들어 봅니다

이제 확정한 한글 의사코드를 바탕으로 AI에게 **한 파일짜리 실행 가능한 초안**을 요청합니다.

**프롬프트 예시 ③ — 단일 파일 초안**

> 확정한 한글 의사코드를 Python **한 파일**로 구현해 주세요. 
> 범위는 데이터 Audit, YOLO 데이터셋 확인, 짧은 Smoke Test까지만입니다. 
> 함수 단위로 구분하고 각 함수의 입력값·반환값·오류 상황을 주석으로 설명해 주세요. 
> 경로와 학습 조건을 설정할 수 있게 해 주세요. 
> 실제 데이터의 내용이나 성능은 임의로 가정하지 마세요. 
> 전체 프로그램이나 GUI를 추가하지 말고 가장 작은 실행 가능한 형태로 작성해 주세요.

**주의:** 한 파일로 만들기는 구조를 이해하기 위한 **학습용 중간 단계**입니다. 실제 프로그램을 끝까지 한 파일로 유지하라는 뜻이 아닙니다.

### 6. 먼저 작은 Smoke Test를 실행하고 기록합니다

Smoke Test는 **프로그램의 기본 실행 흐름이 이어지는지 확인하는 작은 시험**입니다. 높은 mAP를 만드는 시험이 아닙니다.

- 데이터 Audit이 끝나고 치명적인 라벨 오류가 없는지 확인합니다.
- 학습·검증 데이터와 설정 파일이 올바른지 확인합니다.
- 전체 학습 대신 소량 데이터·짧은 Epoch로 실행합니다.
- 모델 로딩, 학습 시작·종료, 결과 파일 저장이 가능한지 확인합니다.

**데이터 유출 방지:** 데이터 분할은 원본/촬영 묶음 등을 고려해서 하고, 증강된 복제본을 Train과 Validation에 나누어 넣지 않습니다. Test 데이터는 최종 평가용으로 따로 보존합니다.

### 7. 코드의 기능 경계를 스스로 정합니다

처음 작성한 파일을 읽고 **각 함수의 책임**을 표시합니다. 분리 기준은 다음과 같습니다.

| 기능        | 역할                                       | 파일 예시                                                       |
| --------- | ---------------------------------------- | ----------------------------------------------------------- |
| 입력        | 파일 찾기, 이미지·라벨 읽기, 입력 확인                  | `input.py`                                                  |
| 전처리       | 프로젝트가 직접 수행하는 데이터 변환                     | `preprocess.py`                                             |
| 핵심 로직   . | 데이터 Audit, Dataset 구성, YOLO 학습·추론, 결과 판정 | `audit.py`, `dataset.py`, `detector.py`,<br>`inspection.py` |
| 출력        | 로그, 검사 결과, 이미지, 보고서 저장                   | `output.py`                                                 |
| 검증        | 위 모든 기능이 기대대로 동작하는지 테스트                  | `tests/` 폴더                                                 |

**정리:** `입력·전처리·핵심 로직·출력`은 **4개의 기능 영역**이고, **검증은 모든 영역에 적용하는 별도의 활동**입니다. 억지로 파일을 정확히 4개만 만들 필요는 없습니다.

또한 처음 Smoke Test의 `학습 파이프라인`과 이후 완성할 `실시간 추론 파이프라인`은 다른 흐름입니다. 처음부터 추론·화면 출력 파일까지 전부 만들 필요는 없습니다.

추론 프로그램으로 확장하면 다음처럼 나눌 수 있습니다.

`이미지 입력 → 필요한 전처리 → YOLO 추론 → 후처리·OK/NG 판정 → 시각화·저장`

**참고:** Ultralytics YOLO가 내부적으로 수행하는 Resize·정규화·NMS 등은 중복 구현하지 않습니다. 별도로 필요한 전처리·후처리만 작성합니다.

### 8. AI가 나누기 전에 내가 먼저 코드를 분리해 봅니다

한 파일의 함수를 역할별 파일로 **직접 옮겨 보고**, import와 함수 호출을 연결합니다. 처음에 틀려도 좋습니다.

각 함수에 대해 다음 네 가지를 말할 수 있어야 합니다.

- 어떤 입력을 받는가?
- 어떤 일을 수행하는가?
- 어떤 값을 반환하거나 파일로 저장하는가?
- 실패하면 어떤 오류를 보고해야 하는가?

스스로 시도한 다음, 막히는 **특정 함수나 연결 부분만** AI에게 질문합니다. 전체 프로젝트를 매번 새로 생성해 달라고 요청하지 않습니다.

### 9. 모듈별 단위 테스트를 작성합니다

실제 YOLO 학습과 GPU가 없어도 확인할 수 있는 로직부터 자동 테스트합니다.

| 대상 | 단위 테스트 예시 |
|---|---|
| 입력 모듈 | 존재하지 않는 경로, 손상된 이미지, 정상 이미지 |
| 데이터 Audit | 라벨 누락, 잘못된 클래스 ID, 잘못된 BBox, 정상 이미지의 빈 라벨 |
| 데이터셋 구성 | 이미지·라벨 매칭, 분할 누락·중복, `data.yaml` 경로 |
| 전처리 모듈 | 크기·채널·자료형, 불필요한 중복 변환 여부 |
| YOLO 호출 모듈 | 실제 모델 대신 가짜(Mock) 객체를 써서 인자 전달·결과 처리 검사 |
| 후처리·판정 | Confidence 경계값, 클래스 필터링, 검출 0개·여러 개 |
| 출력 모듈 | 저장 경로 생성, 결과 파일 내용, 저장 실패 처리 |

**실행 도구 예시:** `python -m pytest -v`  
테스트가 통과해도 **모델 검출 성능이 좋다는 뜻은 아닙니다.** 지금은 코드 로직의 정확성을 점검하는 단계입니다.

### 10. 모듈 연결을 통합 테스트하고 작은 실행을 다시 합니다

개별 모듈이 모두 통과해도 연결 과정에서 오류가 날 수 있습니다. 모듈 분리 후 데이터 Audit → Dataset 구성 → 짧은 학습 흐름을 다시 실행합니다. 추론 모듈까지 개발했다면 소량 이미지를 대상으로 입력 → 예측 → 판정 → 결과 저장을 확인합니다.

`python -m pytest -v`와 `ruff check .` 같은 도구를 사용하고, 테스트가 아직 없는 중요한 분기나 예외 처리도 점검합니다.

### 11. 터미널에서 발견한 오류와 해결 과정을 기록합니다

**디버깅 기록 양식**

- **문제 상황:** 무엇을 실행하다 실패했는가?
- **실행 명령어:** 실제 터미널 명령
- **오류 메시지:** 핵심 에러 원문
- **원인 가설:** 내가 생각한 원인
- **수정 내용:** 변경 파일·함수·이유
- **재검증:** 같은 입력으로 재실행했는가? 단위·통합 테스트는 통과했는가?

AI에게 질문할 때도 **오류 메시지 + 관련 코드 + 예상 결과 + 실제 결과**를 함께 전달합니다. 해결한 뒤에는 원래 실패 상황을 재현하는 테스트를 추가합니다.

### 12. 최적화하기 전 원본과 측정 기준을 보존합니다

정상 동작하는 코드를 Git Commit 등으로 보존한 뒤, 같은 입력·환경에서 **현재 실행 시간과 메모리 사용량**을 기록합니다. 반복 실행이 짧다면 한 번의 측정값만 믿지 않습니다.

먼저 스스로 찾아봅니다.

- 중복 함수나 사용하지 않는 변수·import가 있는가?
- 루프마다 모델을 다시 불러오고 있지는 않은가?
- 같은 이미지를 불필요하게 여러 번 읽거나 변환하지는 않는가?
- 중복 전처리 또는 불필요한 파일 저장이 있는가?
- 코드가 너무 긴 함수에 많은 역할을 몰아넣고 있지는 않은가?

**주의:** 읽기 쉽게 정리하는 **리팩터링**과 속도·메모리를 개선하는 **성능 최적화**는 구분합니다. 먼저 병목을 측정하고 개선할 곳을 정합니다.

### 13. 생성형 AI에게 개선을 요청하되 수정 이유를 확인합니다

**프롬프트 예시 ④ — 코드 리뷰 및 최적화**

> 이 코드는 pytest 테스트를 통과한 기준 버전입니다. 입력·출력·판정 기준은 변경하지 말고, 사용하지 않는 코드·중복 처리·함수 책임 혼합·불필요한 반복 I/O와 모델 재로딩 문제를 찾아 주세요. 먼저 **문제 위치, 이유, 예상 효과, 부작용 위험**을 설명하고, 그다음 필요한 부분만 수정한 코드를 보여 주세요. 성능 향상을 근거 없이 단정하지 말고, 최적화 전후에 비교할 측정 방법과 다시 실행해야 할 테스트도 제안해 주세요.

AI의 변경안을 통째로 덮어쓰기보다 **차이점(diff)을 읽고**, 내가 동의한 부분부터 적용합니다.

### 14. 수정 전후를 비교하고 최종 검증합니다

| 비교 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 동일 입력에 대한 결과 | 기준 기록 | 동일해야 함(의도적으로 바꾸지 않은 경우) |
| 단위 테스트 | 통과 여부 | 다시 통과해야 함 |
| 통합·Smoke Test | 통과 여부 | 다시 통과해야 함 |
| 실행 시간 | 측정값 | 동일 환경에서 재측정 |
| 메모리 사용량 | 측정값 | 동일 환경에서 재측정 |
| 코드 가독성·중복 | 리뷰 메모 | 변경 근거 기록 |

속도가 실제로 빨라지지 않거나 코드를 더 복잡하게 만든다면, AI가 제안한 수정이라도 채택하지 않을 수 있습니다. 모든 개선은 **정상 동작을 유지하면서 측정이나 설명으로 근거를 제시할 수 있어야** 합니다.

- **자동 테스트:** 단위·통합 테스트 및 실행 결과
- **디버깅 기록:** 실패 → 원인 → 해결 → 재검증
- **코드 개선 비교표:** 변경 전후 코드 차이와 측정 결과

## 기억할 핵심 원칙

> **생각은 내가 먼저 하고, AI는 검토와 구현을 도우며, 검증과 선택의 책임은 내가 진다.**  
> **코드를 실행한 것만으로 끝내지 않고, 왜 동작하는지·무엇을 검증했는지·무엇이 개선되었는지를 설명할 수 있어야 한다.**

*보안 주의: 기업 제공 이미지·라벨·모델·민감한 소스코드를 외부 생성형 AI 서비스에 넣기 전에는 제공기관의 보안 및 사용 허용 범위를 확인합니다. 허용되지 않으면 가상 데이터나 일반화한 코드 예시로 질문합니다.*
