## 1. 왜 이러한 데이터 설계가 필요한가요?

예를 들어 웹캠으로 사람이 팔을 들어 올리는 동작을 촬영했다고 가정하겠습니다.

웹캠 영상 자체를 Action Recognition(동작 인식) 모델에 그대로 전달하는 것이 아니라, 
현재 설계한 Skeleton 기반 모델에서는 다음과 같이 변환합니다.

Action Recognition(동작 인식)은 사람의 관절좌표(Keypoint)가 시간에 따라 변하는 패턴을 분석하여 걷기, 뛰기, 팔 들기 등의 동작을 분류하는 AI 기술이며, 이를 수행하는 AI 모델을 
Action Recognition 모델이라고 합니다.

- Raw: 사람의 원본 영상
- 가공: YOLO Pose로 추출한 관절좌표
- 학습 데이터: 정규화한 관절 특징과 시간 순서의 Sequence
- 품질 검사: 관절 누락, 데이터 길이, 클래스 및 데이터 분리 확인
- 모델 입력: 검증된 형태의 Sequence를 Action Recognition 모델에 전달
    

이렇게 하는 이유는 데이터 형식을 일관되게 유지하고, 잘못된 데이터를 걸러내며, 학습과 실시간 추론에서 같은 처리 기준을 적용하기 위해서입니다.

실제로 품질 검사는 마지막에만 하지 않고 원본 수집부터 각 단계에서 수행해야 합니다. 또한 사람별 데이터 분리는 Sequence 생성 전에 계획해야 데이터 누수를 줄일 수 있습니다.

## 2. 데이터는 ERD로 설계해야 할까요?

Skeleton 좌표와 시계열 데이터 자체는 ERD 기반 관계형 테이블을 중심으로 설계할 필요가 없습니다.

대신 데이터를 목적에 따라 나누어 관리하는 것이 좋습니다.

|데이터|권장 저장 방식|목적|
|---|---|---|
|Raw 영상|MP4 파일|원본 보존 및 재처리|
|Keypoint 데이터|JSON, NPZ, Parquet 등|관절좌표 보관|
|Feature·Sequence|NPZ, Parquet 등|AI 모델 학습|
|실시간 관절 데이터|메모리의 Rolling Buffer|즉시 추론|
|추론 결과·이벤트 로그|PostgreSQL 등, 선택|이력 조회·통계|

즉, 실시간 데이터가 들어온다고 해서 모든 프레임을 계속 DB에 저장할 필요는 없습니다.

추천하는 방식은 PC 웹캠에서 YOLO Pose로 관절좌표를 추출하고, 최근 일정 길이의 Sequence만 메모리에 보관한 뒤 FastAPI를 통해 EC2의 Action Recognition 모델에 전달하는 것입니다.

추론 결과 중 필요한 이벤트만 데이터베이스에 저장하면 됩니다. 이 경우 이벤트 이력이나 사용자·장비 정보를 관리하기 위해 작은 ERD를 설계할 수도 있습니다.

제조 프로젝트에서는 ERD·CRUD 중심의 데이터 관리, 산업안전 프로젝트에서는 시계열 AI 데이터 파이프라인 중심의 데이터 설계를 배우도록 구분하면 교육적 차별성이 분명해집니다.
